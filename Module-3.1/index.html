Concept 01 — What Layer 4 does

Your phone runs twenty apps on one connection. Layer 4 is why they don't collide.

The transport layer keeps every conversation separate, chops data into transmittable pieces, and puts it back together at the far end — regardless of what network sits underneath.

Multiplexing combines the streams for transmission. Demultiplexing sorts them out again on arrival.

Managing conversations. Every application starts a conversation, and many run at once on a single host. Layer 4 keeps them distinct so streams don't interfere.

Segmenting and reassembling. Large streams are split into segments in TCP or datagrams in UDP, then rebuilt at the destination.

Header control fields. Source and destination ports, sequence numbers in TCP, length and checksum in UDP.

Port-based identification delivers data to the right application and routes responses back correctly.

Multiplexing and demultiplexing also stop one application monopolising bandwidth.

All of this works independently of the network type, medium or host.

Concept 02 — TCP versus UDP

Get it right, or get it fast. You cannot have both.

TCP checks, confirms, reorders and resends. UDP sends and forgets. Every difference between them traces back to that one decision.

TCP is stateful and connection-oriented with a 20-byte header. UDP is stateless and connectionless with an 8-byte header.

TCP establishes a connection with a three-way handshake before sending anything. It tracks what has been sent and received, acknowledges segments, retransmits what's lost, and reorders what arrives out of sequence. Use it where accuracy matters more than speed — web, email, file transfer, SSH, banking.

UDP sets up nothing, tracks nothing and waits for nothing. Best-effort delivery: no retransmissions, no acknowledgements, no guaranteed order. Data may be lost, duplicated or arrive late.

That's exactly what real-time applications want. Video calls, online games, live streaming and instant messaging all prefer a dropped frame over a delayed one.

DNS and DHCP use UDP too — if no reply comes back, the client just asks again.

Concept 03 — Ports and sockets

The IP address finds the machine. The port finds the program.

Three ranges, assigned by IANA. The destination port names the service you want; the source port is invented on the spot so the reply knows where to land.

A socket is an IP address plus a port number. A socket pair is both ends of one conversation.

The destination port specifies the service being requested on the remote host. Port 80 means HTTP, 443 means HTTPS.

The source port is assigned dynamically by the initiating device. Because every request gets a different one, many conversations run simultaneously without interfering.

IANA splits the range three ways. Well-known 0–1023 for standard services. Registered 1024–49151 for specific applications. Dynamic 49152–65535 assigned by clients on the fly.

Combine address and port and you get a socket. Both sockets together are a socket pair, and that pair is what lets a server keep hundreds of client connections straight.

Concept 04 — The three-way handshake

SYN. SYN-ACK. ACK.

Three messages before a single byte of real data moves. They prove the destination is alive, listening on that port, and ready — and they synchronise the sequence numbers both sides will use.

The handshake validates that the destination host is available and listening on the requested port.

SYN — the client sends a synchronisation request, signalling it wants to start communicating.

SYN-ACK — the server acknowledges that request and sends its own synchronisation in the same message. That's why it's three messages rather than four.

ACK — the client acknowledges the server's response. The connection now exists and data can flow.

The Maximum Segment Size is negotiated during this exchange too.

Because TCP is stateful, both ends now hold a record of the connection. That's the overhead UDP refuses to pay.

    Concept 05 — Closing the connection

    Four messages to shut down, not three.

    Each direction has to be closed separately, because either side may still have data to send. FIN, ACK, FIN, ACK — and either end can start it.

    Two FINs and two ACKs. Four messages total.

    The initiating side sends FIN, signalling it has finished sending data. The other side replies ACK, confirming it received the signal.

    That closes one direction only. The second side then sends its own FIN, and the first side replies with a final ACK.

    Both pairs are needed so that each side confirms it has finished transmitting and all outstanding data has been acknowledged. Orderly termination stops sessions lingering open as a security risk.

    Either the client or the server can initiate it. The module's example has the client going first, but that's a convention, not a rule.

    Unexplained open connections are worth investigating — netstat lists active sessions and open ports, and netstat -n shows raw numbers instead of resolved names, which is usually more useful for security analysis.

      Concept 06 — Sequence numbers and ACKs

      The acknowledgement number tells you what's expected next, not what arrived.

      Receive bytes 1 to 10 and you acknowledge with 11. That off-by-one is deliberate, it's called expectational acknowledgement, and it's the single most misread number in TCP.

      Host A sends bytes 1–10. Host B replies ACK 11. Eleven, not ten.

      Every segment carries a sequence number marking its position in the overall stream, so the receiver can reorder anything that arrives out of sequence.

      Sequencing starts from a random Initial Sequence Number. Randomising it makes connection hijacking harder, because an attacker can't guess what comes next.

      The sequence number then increments by the number of bytes transmitted, not by one per segment.

      Expectational acknowledgement: the ACK number names the next byte the receiver wants. It confirms everything before it arrived intact.

      Selective Acknowledgement, when both ends support it, lets the receiver acknowledge non-contiguous blocks — so only the genuinely missing segments get resent, not everything after the gap.

      Concept 07 — Flow control and congestion

      Two different problems that look identical from the sender's chair.

      Flow control protects the receiver from being overwhelmed. Congestion control protects the network in between. Both work by sending less — for entirely different reasons.

      Flow control is about the receiver's buffer. Congestion control is about the routers in the middle.

      Window size in the TCP header says how many bytes the sender may transmit before waiting for an acknowledgement. It stops buffer overflow at the receiving end.

      The sliding window lets the receiver change that number during the session as its buffer fills or drains, reporting the new figure in each acknowledgement.

      MSS is the largest payload a single segment can carry without exceeding the network's MTU and being fragmented. On Ethernet with a 1500-byte MTU the default MSS is 1460 bytes — 1500 minus 20 bytes of IP header and 20 of TCP header. It's negotiated during the handshake.

      Congestion is different: routers overwhelmed with traffic start dropping packets. Slow start begins conservatively and ramps up. Once stable, congestion avoidance increases the rate far more gradually while watching for trouble.

      Concept 08 — The application layer

      Three OSI layers collapse into one in TCP/IP.

      Application, presentation and session are separate boxes in OSI. TCP/IP merges them. Underneath sits a set of protocols you identify by port number.

      Application defines the protocols. Presentation formats. Session manages the dialogue.

      Application — defines network protocols and services, and interfaces directly with end-user software.

      Presentation — data formatting, compression and encryption, so different systems can interoperate. It covers media standards like MKV, MOV and MPG for video, GIF, JPG and PNG for images.

      Session — initiates, maintains and recovers communication sessions to keep exchanges stable.

      In TCP/IP, all three become a single Application Layer. The functions don't disappear; the boundaries do.

      Both ends must run compatible application layer protocols or nothing works, regardless of how healthy the lower layers are.

      Concept 09 — Email and the web

      POP3 takes your mail away. IMAP leaves it where it is.

      One protocol sends, two retrieve, and the two retrievers behave completely differently the moment you own a second device.

      SMTP sends. POP3 downloads and deletes. IMAP synchronises.

      SMTP, port 25, transmits outgoing mail from client to server and between servers. It's one-way — sending only — with store-and-forward queuing and error handling that returns failed mail to the sender.

      POP3, port 110, downloads mail to the local device and removes it from the server by default. One-way synchronisation, offline access, no central storage. Unsuitable for multiple devices.

      IMAP, port 143, leaves messages on the server and downloads copies. Two-way synchronisation, so a change on one device shows up everywhere.

      On the web, HTTP on port 80 sends everything in the clear. HTTPS on port 443 wraps it in SSL/TLS, giving privacy, integrity and authentication — verifying you reached the real server, which is what defeats man-in-the-middle attacks.

      Methods: GET retrieves, POST sends new data, PUT updates existing data.

      Concept 10 — DNS and DHCP

      One finds addresses for names. The other hands out addresses entirely.

      DNS walks a hierarchy from root to authoritative server. DHCP runs a four-step conversation every device has before it can speak at all.

      DNS: cache, resolver, root, TLD, authoritative. DHCP: Discover, Offer, Request, Acknowledge.

      DNS translates a domain name into an IP address. The device checks its local cache first. If that misses, the query goes to a resolver, usually run by an ISP.

      The resolver asks a root server, which points to the right TLD server for .com or .org. The TLD server points to the authoritative nameserver for that domain, which finally returns the address.

      nslookup queries DNS directly and is the tool for troubleshooting resolution failures.

      DHCP assigns addresses plus subnet mask, gateway and DNS servers automatically. Remember it as DORA: Discover, Offer, Request, Acknowledge.

      Discover is a broadcast — the client has no address yet, so it can't do anything else.
